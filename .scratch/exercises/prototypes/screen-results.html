// Carries the Set editor's Training exercise to the Training editor below it. A singleton, so a result outlives a
// configuration change; the unlimited buffer holds it until the Training editor collects.
class TrainingExerciseResults {
    private val channel = Channel<TrainingExerciseResult>(Channel.UNLIMITED)
    val results: Flow<TrainingExerciseResult> = channel.receiveAsFlow()

    fun send(result: TrainingExerciseResult) {
        channel.trySend(result)
    }
}
Same shape as AppNavigator, which already queues requests on a Channel. A channel hands each result to exactly one collector, so a result can't be delivered twice.

3 AppNavigator carries results next to requests app/…/AppNavigator.kt CHANGED

class AppNavigator {
    private val _requests = Channel<NavRequest>(Channel.UNLIMITED)
    val requests: Flow<NavRequest> = _requests.receiveAsFlow()

    // Every receiver sees every result and keeps its own type. A result reaches only ViewModels collecting at
    // that moment; the Screen it returns to is below on the stack, so its ViewModel is alive and collecting.
    private val _results = MutableSharedFlow<NavResult>(extraBufferCapacity = 1)
    val results: Flow<NavResult> = _results

    fun push(key: NavKey) { _requests.trySend(NavRequest.Push(key)) }
    fun pop(key: NavKey) { _requests.trySend(NavRequest.Pop(key)) }

    fun popTo(keyType: KClass<out NavKey>, result: NavResult? = null) {
        result?.let { _results.tryEmit(it) }              // emitted before the pop is requested
        _requests.trySend(NavRequest.PopTo(keyType))
    }
}
One stream for all results, so nothing grows per result type. A broadcast (SharedFlow) rather than a Channel: a channel hands each item to one collector, so with two receivers the wrong one could take and drop the other's result. (KClass remains only for the popTo target, which the architecture ticket already needs.)
