# Architecture for Exercises and Training exercises

Type: grilling
Status: resolved
Blocked by: 04

## Question

How is this built? At least:

- What lives in `feature/exercises` (catalogue, picker screens) versus `feature/trainings` (Training exercise, Set,
  Set editor?), and how they connect without feature-to-feature coupling.
- Navigation keys and arguments along category picker → Exercise picker → Set editor and back to the Training editor.
- How the Training editor holds unsaved changes (name + Training exercises) and how the Set editor's result reaches
  them across Screens; saving a Training with its Training exercises atomically; restoring them with the Training
  list's „Cofnij”; repository methods, Room entities and relations, stable Exercise ids, the destructive schema change.
- Where the timed flag lives on Exercises; the discard dialog („Odrzucić zmiany?”) in `:core:design-system`.
- Updating `android-presentation-mvi` where it requires surviving process death: unsaved changes may be lost (see
  [Training exercise and Set rules](04-training-exercise-and-set-rules.md)).
- New design-system components. Candidates from the three prototypes: the tappable value pill with a focused
  state, a count stepper (− N +), hold-to-repeat ± buttons, the count badge on Exercise category rows.

Updates any `android-*` skill a decision overrides.

## Answer

Resolved with the user on 2026-11-13, except how a result returns from one Screen to another: split out into
[Returning a result from one Screen to another](07-screen-results.md), which the user wants handled with care.

### Modules

- **`:core:domain`** (new, pure JVM) holds what both features share: `Exercise(id, name, category, isTimed)`,
  `ExerciseCategory(id, name)` and the `ExerciseCatalogue` interface (`categories()`, `exercises(categoryId)`,
  `exercise(id)`), synchronous while the catalogue is constants.
- **`:feature:exercises:data`** holds the hardcoded catalogue implementing `ExerciseCatalogue`, bound in Koin.
  **`:feature:exercises:presentation`** holds the Exercise category picker and Exercise picker. No
  `:feature:exercises:domain` (it would be empty). User-defined Exercises later swap only the implementation to Room.
- Ids are `Long` constants (1, 2, …) for Exercises and Exercise categories, so a later Room table can seed them as
  they are. Names are plain Polish `String`s in the catalogue (data, not string resources). `isTimed` is true only for
  Plank and Deska boczna.
- **`feature:trainings`** holds the Set editor. Domain: `TrainingExercise(exercise: Exercise, sets:
  List<ExerciseSet>)`, `ExerciseSet(reps: Int, weightGrams: Int)`; `Training` gains `exercises`. The code says
  `ExerciseSet` to avoid `kotlin.collections.Set`; the glossary term stays **Set**. Grams keep 1.5 kg steps exact.

### Navigation

- One key per Screen; only `:app` names another feature's key, through screen navigators:
  - „Dodaj ćwiczenie”: `TrainingEditorNavigator.openExercisePicker()` → `:app` pushes `ExerciseCategoryPickerKey`.
  - Category tap → `ExercisePickerKey(categoryId)` within the exercises feature.
  - Exercise tap: `ExercisePickerNavigator.onExercisePicked(exerciseId)` → `:app` pushes `SetEditorKey(exerciseId)`.
  - Training exercise row tap → `SetEditorKey(exerciseId, index, sets)`.
- `SetEditorKey.index == null` is add mode, starting at 3 × 0 kg × 12; otherwise the key carries the edited
  Training exercise's Sets and its position.
- „Dodaj do treningu” leaves the Set editor and both pickers at once through a new `AppNavigator.popTo(key)` /
  `NavRequest.PopTo` (removes entries above the topmost key); `SetEditorNavigator.backToTraining()` uses it in `:app`.
  Back from the Set editor still lands on the Exercise picker; „Gotowe” in edit mode pops itself.
- **Settled later**: how the Set editor's Training exercise reaches the Training editor's unsaved changes, and one
  `backToTrainingEditor(result)` for both modes, see
  [Returning a result from one Screen to another](07-screen-results.md).

### Storage

- Three tables, autogenerated ids: `trainings`; `training_exercises(id, training_id FK ON DELETE CASCADE,
  exercise_id)`; `exercise_sets(id, training_exercise_id FK ON DELETE CASCADE, reps, weight_grams)`. Read through a
  `@Relation` class; children sorted by id in the mapper (a save deletes and reinserts them, so id order is added
  order; no position column).
- `@Transaction` DAO methods insert a Training with its exercises and replace a Training's exercises, so „Zapisz” is
  all or nothing. Deleting a Training cascades; „Cofnij” reinserts the kept `Training` with every row's old id.
- Repository: `observeTrainings()` and `getTraining(id)` return Trainings with exercises, mapping `exercise_id` to an
  `Exercise` through `ExerciseCatalogue`; writes are `addTraining(name, exercises)`, `updateTraining(training)`
  (replaces its exercises), `deleteTraining(id)`, `restoreTraining(training)`.
- The database stays at version 1: the committed schema JSON is overwritten and the user clears the app's data once.
  No `fallbackToDestructiveMigration`, which would silently wipe data on any later version bump.

### Presentation and design system

- Each editor's ViewModel keeps its starting values; `hasChanges` compares current to starting state by value. A
  `BackHandler` in the Root sends `OnBackClick`; the ViewModel goes back or shows the discard dialog.
- New `:core:design-system` components, one ticket each: `AppValuePill` (tappable, focused state),
  `AppRepeatIconButton` (hold-to-repeat ±), `AppCountStepper` (− N +, on the repeat button), `AppCountBadge`,
  `AppDiscardDialog(onDiscard, onDismiss)` with its strings in design-system resources. Picker rows reuse or extend
  `AppListRow`.
- `android-presentation-mvi` updated: unsaved input, including changes spanning several Screens, is lost on process
  death; no `SavedStateHandle`.

**Additions**: none.
