Letting the ViewModel navigate

Three ways to do it, shown on the Training list → Training editor flow.

Today: the problem

tap Edit→Action→ Root handles it (navigates)+ViewModel handles it (closes sheet)

Root

onAction = { action ->
    when (action) {
        OnAddClick -> onAddTraining()
        is OnEditClick -> onEditTraining(action.trainingId)
        else -> Unit
    }
    viewModel.onAction(action)
}

ViewModel

when (action) {
    is OnEditClick -> dismissOptionsSheet()  // half of the story
    OnAddClick -> Unit                       // does nothing
    ...
}

One tap, two handlers. To know what Edit does you read two files, and the ViewModel has branches that do nothing.

Option A: Navigator least code

One small Navigator class, shared by the whole app. ViewModels get it injected and call push / pop. AppNavDisplay listens and moves the back stack.

tap Edit→Action→ViewModel→ Navigator→AppNavDisplay moves the back stack

ViewModel: the whole story in one place

class TrainingListViewModel(
    private val repository: TrainingRepository,
    private val navigator: Navigator,
) : ViewModel() {

    fun onAction(action: TrainingListAction) {
        when (action) {
            OnAddClick -> navigator.push(TrainingEditorKey())
            is OnEditClick -> {
                dismissOptionsSheet()
                navigator.push(TrainingEditorKey(action.trainingId))
            }
            ...
        }
    }
}

// editor
OnBackClick -> navigator.pop(key)
// after save, or Training missing:
navigator.pop(key)   // TrainingSaved / TrainingMissing Events disappear

Root and entries: nothing left to wire

@Composable
internal fun TrainingListRoot(viewModel: TrainingListViewModel = koinViewModel()) {
    ...
    TrainingListScreen(state = state, onAction = viewModel::onAction)
}

fun EntryProviderScope<NavKey>.trainingsEntries() {
    entry<TrainingListKey> { TrainingListRoot() }
    entry<TrainingEditorKey> { key -> TrainingEditorRoot(key) }

Written once per app (~20 lines)

// :core:presentation
class Navigator {
    private val _commands = Channel<NavCommand>(Channel.BUFFERED)
    val commands = _commands.receiveAsFlow()
    fun push(key: NavKey) { _commands.trySend(NavCommand.Push(key)) }
    fun pop(key: NavKey) { _commands.trySend(NavCommand.Pop(key)) }
}

// :app, inside AppNavDisplay
ObserveAsEvents(navigator.commands) { command ->
    when (command) {
        is NavCommand.Push -> backStack.push(command.key)
        is NavCommand.Pop -> backStack.pop(command.key)
    }
}
  • A new navigation is one line in the ViewModel. No callback, no Event, no entry wiring.
  • Roots have no navigation parameters; onAction = viewModel::onAction everywhere.
  • Existing push / pop guards and state restoration stay as they are.
  • Same Navigator file copies into any app.
  • The ViewModel must be able to see the key it opens. Fine inside a feature; opening another feature's screen needs an extra rule (see Option C, or shared keys).
  • One app-wide object every ViewModel can reach.

Option B: navigation as Events no new concept

The ViewModel handles every Action alone and, when it wants to navigate, sends an Event. The Root turns that Event into the callback it already has. It is the pattern the editor uses today for TrainingSaved, applied to all navigation.

tap Edit→Action→ViewModel→ Event→Root→callback→entries move the back stack

ViewModel

when (action) {
    OnAddClick -> send(TrainingListEvent.OpenEditor(null))
    is OnEditClick -> {
        dismissOptionsSheet()
        send(TrainingListEvent.OpenEditor(action.trainingId))
    }
    ...
}

Root and entries

ObserveAsEvents(viewModel.events) { event ->
    when (event) {
        is OpenEditor -> onOpenEditor(event.trainingId)
        is TrainingDeleted -> ...
    }
}
TrainingListScreen(state = state, onAction = viewModel::onAction)

// entries: unchanged
TrainingListRoot(onOpenEditor = { id -> backStack.push(TrainingEditorKey(id)) })
  • Nothing new to learn or copy between apps: only Events and callbacks.
  • ViewModels know nothing about keys or the back stack; features stay fully isolated.
  • Opening another feature's screen works the same way as today.
  • Most code per navigation: an Event, a Root branch, a callback parameter, an entry lambda (4 places).
  • The Root still handles navigation, just from Events instead of Actions.

Option C: a navigator interface per feature most structure

Each feature declares what navigation it needs as an interface. ViewModels call it. :app implements it (using Option A's Navigator underneath).

tap Edit→Action→ViewModel→ TrainingsNavigator (interface)→implementation in :app→back stack

Feature

interface TrainingsNavigator {
    fun openEditor(trainingId: Long? = null)
    fun closeEditor(key: TrainingEditorKey)
}

// ViewModel
OnAddClick -> navigator.openEditor()
is OnEditClick -> {
    dismissOptionsSheet()
    navigator.openEditor(action.trainingId)
}

:app

class AppTrainingsNavigator(
    private val navigator: Navigator,
) : TrainingsNavigator {
    override fun openEditor(trainingId: Long?) =
        navigator.push(TrainingEditorKey(trainingId))
    override fun closeEditor(key: TrainingEditorKey) =
        navigator.pop(key)
}
// + a Koin binding
  • ViewModel code reads as intent (openEditor) and never touches keys.
  • Cross-feature navigation needs no extra rule: :app sees every key.
  • Roots are as empty as in Option A.
  • An interface, an implementation and a binding per feature, on top of Option A's Navigator.
  • A new navigation touches 3 places instead of 1.
