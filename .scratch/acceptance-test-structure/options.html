Splitting the acceptance suite by screen

Today: one test class (11 cases), one DSL (16 methods), one UI driver (17 methods), all named after the Trainings feature. You already decided two things: test classes per screen and drivers per screen. What is still open is the layer between them, the DSL, and that is where the three options differ.

Shared plumbing

The Compose extension, InMemoryAppExtension and the scope function move out of the test class into one AcceptanceTest base class, so a new screen's test class is just its cases.

addTraining spans both screens (open from list, type and save in editor). No driver owns it; the DSL composes it from the two drivers. Drivers never reference each other.

Option A · Feature DSL over screen drivers

Files

acceptance/
  AcceptanceTest.kt                    new, base class
  trainings/
    TrainingsAcceptanceTest.kt
    TrainingListAcceptanceTest.kt      new
    TrainingEditorAcceptanceTest.kt    new
  dsl/
    TrainingsDsl.kt                    kept, one per feature
  driver/
    TrainingsUiDriver.kt
    TrainingListUiDriver.kt            new
    TrainingEditorUiDriver.kt          new

Trade-offs

  • Matches the acceptance-testing skill as written: one DSL per feature, domain words only.
  • Moving a button to another screen changes the DSL's wiring, not a single test line.
  • The DSL is still one class per feature. A feature with five screens gets a 60-method DSL, which is the very problem you want gone, only with shorter methods.
  • Method names must carry the screen themselves (assertNewTrainingScreenIsEmpty) to stay unambiguous in one flat namespace.

A test case

class TrainingEditorAcceptanceTest : AcceptanceTest() {
    @Test
    fun `saving the new training screen lists the training at the end`() =
        trainings {
            givenTrainings("Push day")
            openNewTrainingScreen()
            enterName("Nogi")
            save()
            assertTrainingsListed("Push day", "Nogi")
        }
}

The DSL

class TrainingsDsl(
    private val list: TrainingListUiDriver,
    private val editor: TrainingEditorUiDriver,
) {
    fun givenTrainings(vararg names: String) =
        names.forEach { name ->
            list.openNewTraining(); editor.awaitShown()
            editor.typeName(name); editor.save()
        }
    fun delete(name: String) = list.deleteTraining(name)
    fun enterName(name: String) = editor.typeName(name)
    // … every screen's vocabulary, in one class
}

Option B · Screen DSLs, steps prefixed with the screen

Files

acceptance/
  AcceptanceTest.kt                    new, base class
  AppDsl.kt                            new, holds every screen DSL
  trainings/
    TrainingsAcceptanceTest.kt
    TrainingListAcceptanceTest.kt      new
    TrainingEditorAcceptanceTest.kt    new
  dsl/
    TrainingsDsl.kt
    TrainingListDsl.kt                 new
    TrainingEditorDsl.kt               new
  driver/
    TrainingsUiDriver.kt
    TrainingListUiDriver.kt            new
    TrainingEditorUiDriver.kt          new

Trade-offs

  • Every layer grows by adding files, never by lengthening one. A new screen is three small files plus one line in AppDsl.
  • Each line of a test says which screen it happens on, so a cross-screen case reads as a route.
  • Autocomplete after trainingList. shows only that screen's steps, with shorter names (assertListed, not assertTrainingsListed).
  • Flat: no nesting inside the test body.
  • Test cases now know the screen map. Moving "delete" from the list to a detail screen edits every test that deletes. (You accepted most of this already by filing tests per screen.)
  • Departs from the skill's "one DSL per feature"; the skill needs an edit.
  • The prefix repeats on runs of steps on the same screen.

The DSLs

class AppDsl(compose: ComposeContext, resources: Resources) {
    private val list = TrainingListUiDriver(compose, resources)
    private val editor = TrainingEditorUiDriver(compose, resources)
    val trainingList = TrainingListDsl(list, editor)
    val trainingEditor = TrainingEditorDsl(editor)
}

class TrainingListDsl(
    private val list: TrainingListUiDriver,
    private val editor: TrainingEditorUiDriver,  // for givenTrainings
) {
    fun givenTrainings(vararg names: String) = /* as in A */
    fun openNewTraining() { list.openNewTraining(); editor.awaitShown() }
    fun delete(name: String) = list.deleteTraining(name)
    fun assertListed(vararg names: String) = list.assertListedInOrder(names.toList())
}

Option C · Screen DSLs, one block per screen

Files

Identical to option B. Only AppDsl differs: it exposes functions taking a block instead of properties.

class AppDsl(…) {
    fun trainingList(steps: TrainingListDsl.() -> Unit) = listDsl.steps()
    fun trainingEditor(steps: TrainingEditorDsl.() -> Unit) = editorDsl.steps()
}

Trade-offs

  • Same file-growth story as B.
  • Screen changes are visible as block boundaries; no repeated prefix inside a block.
  • The familiar "robot pattern" from Android testing talks.
  • Two levels of nesting in every test; short cases get taller, and a case that bounces list → editor → list becomes three blocks for five steps.
  • Inside a nested block the outer scope's functions are still callable unless a @DslMarker annotation is added, one more thing to maintain.
  • Same coupling to the screen map, and the same skill edit, as B.
